# Xcode project and build settings

How a TSH iOS project is laid out: the project file, targets, build configurations,
`.xcconfig` files, schemes, signing, `Info.plist`, the privacy manifest and
localization. Swift language mode and concurrency settings have their own reference:
[`swift-language-mode-and-concurrency.md`](./swift-language-mode-and-concurrency.md).

## 1. The project file

**A plain Xcode project, edited in Xcode, with buildable folders.** Since Xcode 16,
folders in the project navigator can be *buildable* (synchronized) folders: Xcode
mirrors the directory on disk instead of listing every file in the project file.
Adding, moving or deleting a source file then changes nothing in the project file,
which removes most project-file merge conflicts.

- New project: keep the template's buildable folders.
- Existing project with classic groups: convert a group to a folder (Xcode's
  *Convert to Folder* on a group) one group at a time, in its own change, when the
  merge-conflict cost justifies it. Not as a side effect of another task.
- **A project generated by XcodeGen or Tuist keeps its generator.** Edit
  `project.yml` / `Project.swift`, regenerate, and never commit hand edits to the
  generated project — the next generation erases them.

### The JSON project format (Xcode 27.2)

Xcode 27.2 adds a JSON project file, `project.xcproj`, replacing `project.pbxproj`
inside the same `.xcodeproj` bundle. New projects use it by default. An existing
project keeps `project.pbxproj` until converted in the File inspector (**Project
Document → Project Format → JSON**). A converted project opens in every Xcode 27
release, including those before 27.2; Xcode 26 and earlier cannot open it. The format
is open source at [apple/xcode-project-format](https://github.com/apple/xcode-project-format).

Before converting an existing project:

1. Every developer machine and CI runner must be on Xcode 27 or later.
2. No release branch that still builds with Xcode 26 may need the converted file.
3. Every tool that reads or writes `project.pbxproj` — XcodeGen, Tuist, fastlane
   actions, CI scripts that `grep` build settings — must support the new format.
   fastlane's project tooling (the `xcodeproj` gem) did not read it at the time of
   writing; check the version you run.
   Convert on a branch and run the full pipeline before merging.

Converting is its own change, never part of a feature.

## 2. Targets

| Target | When |
| --- | --- |
| App | Always one per shipped app. Starts with feature folders inside the app target; once the app grows, features move into local packages and the target keeps little beyond the `@main` entry point, composition root and resources ([`swift-package-manager.md`](./swift-package-manager.md)) |
| Unit test bundle | Always. Hosted by the app only when a test needs the app's runtime; otherwise package tests run without a host |
| UI test bundle | When the project has UI tests |
| Extensions (widgets, share, notification service…) | One target per extension, sharing code through packages, never through file membership in two targets |

A source file that is a member of two targets compiles twice and drifts silently.
Share code through a package instead.

## 3. Build configurations and `.xcconfig` files

**Build settings live in committed `.xcconfig` files**, one per configuration, so
they are reviewable in a diff and identical for everyone.

```text
Configurations/
├── Shared.xcconfig        # settings every configuration shares
├── Debug.xcconfig         # #include "Shared.xcconfig"
├── Staging.xcconfig       # optional; #include "Shared.xcconfig"
└── Release.xcconfig       # #include "Shared.xcconfig"
```

- Assign each file to its configuration on the project (Project → Info →
  Configurations), then **remove the same settings from the build-settings editor**:
  a value set in the project file silently overrides the `.xcconfig`, which is the
  most common reason "the setting did nothing".
- Configurations are **Debug** and **Release**. Add **Staging** only when the app
  must point at a different backend in a distributable build. One configuration per
  environment, not per developer.
- Environment values the app reads at runtime (API base URL, feature flags) go into
  an `.xcconfig` variable, surfaced through an `Info.plist` key, and read once at
  start-up into a typed configuration value.

```text
// Staging.xcconfig
#include "Shared.xcconfig"
API_BASE_URL = https:/$()/api.staging.example.com
```

`//` starts a comment in an `.xcconfig`, which is why a URL needs the `$()` break.

### Secrets

Nothing secret is committed: not in an `.xcconfig`, `Info.plist`, scheme, or source
file. And anything compiled into the app bundle can be read by anyone who downloads
it — so a value that must stay secret (a third-party API secret, a signing key) does
not belong in the app at all; the app talks to a backend that holds it. Publishable
identifiers (an analytics write key, a public client ID) may ship in the bundle.

## 4. Schemes

- One **shared** scheme per app target, committed under
  `<Project>.xcodeproj/xcshareddata/xcschemes/`. CI builds by scheme name, and a
  scheme that exists only in one person's `xcuserdata` breaks CI.
- Run → Debug configuration; Archive → Release. A Staging scheme only when the
  Staging configuration exists.
- Do not encode environment differences in scheme environment variables: they do
  not exist in an archived build.

## 5. Signing basics

- **Automatic signing** for development, with `DEVELOPMENT_TEAM` and
  `PRODUCT_BUNDLE_IDENTIFIER` set in the `.xcconfig`.
- Bundle identifiers per configuration when Staging and Release must install side by
  side (`com.example.app.staging`).
- Certificates, private keys and App Store Connect API keys live in the CI secret
  store or a dedicated signing tool, never in the repository.
- Distribution signing and release automation are out of this skill's scope.

## 6. `Info.plist`

New projects generate `Info.plist` from build settings (`GENERATE_INFOPLIST_FILE =
YES`, with `INFOPLIST_KEY_*` settings). Keep that until the app needs a key the
generator does not cover; then add an `Info.plist` file holding only the extra keys.

Every permission prompt needs its usage-description key
(`NSCameraUsageDescription`, `NSLocationWhenInUseUsageDescription`, …) with a
sentence that says why the app needs it. A missing key crashes the app at the moment
it asks.

## 7. Privacy manifest

Every app target ships a `PrivacyInfo.xcprivacy` when the app or its code uses a
**required-reason API** (for example `UserDefaults`, file timestamps, system boot
time, disk space) — which practically every app does. It declares:

- the required-reason APIs used and the approved reason for each;
- the data the app collects and whether it is used for tracking;
- tracking domains, if any.

Third-party SDKs on Apple's list must ship their own manifest; check it when adding
or updating one. Generate the privacy report from an archive (Organizer → *Generate
Privacy Report*) before a release to see the merged result.

## 8. Localization

Use **String Catalogs** (`.xcstrings`) for every user-facing string, including in
packages (`defaultLocalization` in `Package.swift`). Xcode extracts strings at build
time and flags stale and missing translations. Migrate a legacy `.strings` file to a
catalog when you next touch it, not as a drive-by.
