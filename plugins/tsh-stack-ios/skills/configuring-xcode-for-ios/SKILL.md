# Configuring Xcode for iOS

TSH's recommended build setup for a **native iOS app**: which Xcode and Swift to
use, how the project, targets and build configurations are laid out, the Swift
language mode and concurrency settings, dependencies through Swift Package Manager,
and the `xcodebuild` commands CI runs.

This skill is about **configuration**. How app code is written — SwiftUI views,
state, navigation, networking, persistence, and concurrency *in code* — belongs to
the sibling skill [`implementing-ios`](../implementing-ios/SKILL.md). What tests
assert is out of scope too; this skill only makes sure CI runs them. Release
pipelines (TestFlight, App Store submission, certificate management at scale) are
not covered. Neither is the `ios/` project that React Native or Flutter generates:
its Podfile and build settings are managed by that framework's tooling (React
Native autolinks through CocoaPods), so this skill's rules on dependencies and
settings would be wrong advice there.

## Version Baseline

Written against **Xcode 27.2, Swift 6.4 and the iOS 27.2 SDK**, current as of
November 2026. Before applying anything, read what the repository pins:

```shell
xcodebuild -version                       # the Xcode actually selected
cat .xcode-version 2>/dev/null            # the team's pin, if any
xcodebuild -showBuildSettings -scheme <App> | grep -E 'SWIFT_VERSION|IPHONEOS_DEPLOYMENT_TARGET|SWIFT_DEFAULT_ACTOR_ISOLATION|SWIFT_APPROACHABLE_CONCURRENCY'
head -1 Package.swift                     # swift-tools-version of each package
```

- **The project pins an Xcode or Swift** → follow it; an upgrade is its own change.
- **Greenfield** → the latest stable Xcode, Swift 6 language mode.
- **Any version fact here matters to the task** → check the current Xcode release
  notes and swift.org — through `context7`, which `tsh-core` bundles, or
  developer.apple.com directly. Where they disagree with this skill, the
  documentation wins.

App Store Connect has required uploads built with **Xcode 26 or later and an iOS 26
SDK** since 28 April 2026. That governs the SDK you build with, not the deployment
target — the oldest iOS the app runs on is a separate decision.

## Applicability and Precedence

Read the project before proposing anything: the `.xcodeproj`/`.xcworkspace`, every
`.xcconfig`, `Package.swift` files, `Podfile` or `Cartfile`, `.swiftformat`, `.swift-format` or
`.swiftlint.yml`, and the CI workflow. **Local conventions outrank this skill's
defaults.** Apply these defaults where the project is silent, and record a
deliberate deviation rather than mixing styles.

**The defaults below are for new projects, not a verdict on existing ones.** A
working project that differs is not a defect. Propose the smallest staged change
that serves the task and name the remaining gap. A project generated by XcodeGen or
Tuist is edited through its manifest, never by hand in Xcode.

## Non-negotiable Rules

| Severity | Rule |
| --- | --- |
| MUST | In an existing project, make the smallest staged change and record the remaining gap. Never rewrite a working project, its build settings or its dependency manager wholesale to match this skill. |
| MUST | Ask for the deployment target when the project has none or the user has not stated one. It decides which devices and users the app reaches — a business decision, not a default to pick silently. |
| MUST | New targets and packages use **Swift 6 language mode**. An existing Swift 5-mode codebase migrates module by module with complete checking as warnings first — never the whole app in one change. |
| MUST | Add dependencies through **Swift Package Manager** and commit `Package.resolved`. No new CocoaPods or Carthage dependency: CocoaPods trunk goes read-only on 2 December 2026. |
| MUST | Keep build settings in committed `.xcconfig` files, one per configuration, rather than scattered through the Xcode build-settings editor. |
| NEVER | Commit a secret — API key, signing private key, `.p8`, `.p12`, provisioning credentials — in an `.xcconfig`, `Info.plist`, scheme or source file. Anything shipped in the app bundle can be extracted, so a real secret does not belong in the app at all. |
| MUST | Ship a `PrivacyInfo.xcprivacy` in every app target that uses a required-reason API, and keep it in step with the third-party SDKs the app links. |
| MUST | CI builds and tests with `xcodebuild` on a pinned Xcode, using the committed `Package.resolved` only, and fails on compiler warnings. |
| MUST | Run one formatter — SwiftFormat in a new project, pinned through a build-tools package — configured by a committed file, in CI. Two formatters fighting over the same files is a defect. |

## Procedure

**Step 1 — Read the ground truth.** Run the Version Baseline commands. List the
targets, configurations and schemes (`xcodebuild -list`), the dependency manager in
use, and what CI actually runs.

**Step 2 — Decide greenfield or brownfield.** A new project takes the defaults as
written. An existing one gets the smallest staged change — state what you are
deliberately leaving alone.

**Step 3 — Settle the open decisions first.** No deployment target → ask (rule
above). Read
[`xcode-version-and-upgrades.md`](./references/xcode-version-and-upgrades.md)
before recommending one, and
[`swift-language-mode-and-concurrency.md`](./references/swift-language-mode-and-concurrency.md)
before touching `SWIFT_VERSION` or any concurrency setting.

**Step 4 — Load the reference for the change.** Read
[`xcode-project-and-build-settings.md`](./references/xcode-project-and-build-settings.md)
before editing the project or an `.xcconfig`, and
[`swift-package-manager.md`](./references/swift-package-manager.md) before adding a
dependency or a package.

**Step 5 — Check the gate**, when the change touches build settings or CI. Confirm CI
builds and tests on a pinned Xcode and fails on warnings — read
[`formatting-linting-and-ci.md`](./references/formatting-linting-and-ci.md). A
setting nobody's build enforces is a suggestion.

**Step 6 — Apply the smallest change.** Prefer an `.xcconfig` edit over the build
settings editor, and say when a change alters runtime behaviour — default isolation
and `nonisolated(nonsending)` do, not only diagnostics.

**Step 7 — Verify.** Run the clean build and the test suite with the same
`xcodebuild` command CI uses, and launch the app in the Simulator after any change
to the deployment target, isolation defaults or linked packages: a green build does
not prove the app still starts.
